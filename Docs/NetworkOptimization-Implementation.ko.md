# 네트워크 풀링·발사·조작감 개선

작성일: 2026-10-08. 사용자 제공 「Netcode 샘플의 부드러운 이동과 본 프로젝트 끊김 원인 분석」을 참고했다. 샘플의 CharacterController/Distributed Authority를 그대로 옮기지 않고 기존 Rigidbody2D/Host–Client 구조를 유지했다.

## 적용 사항

### 총알

- 원격 클라이언트는 공격 입력 시 풀에서 **시각 전용 예측 탄환**을 즉시 꺼낸다. 예측 객체에는 NetworkObject/Collider/피해 판정이 없다. 호스트는 원래 서버 탄환을 즉시 생성하므로 예측 탄환을 중복 생성하지 않는다.
- 요청에 발사 시퀀스와 총구 좌표를 포함한다. 서버는 유한한 좌표·방향, 중복 시퀀스, 다운 상태, 발사 간격을 확인한다. 총구 좌표는 서버 복제 위치 주변의 제한 범위(이동속도 × 0.25초 + 0.5 유닛) 안에서만 수용한다. 임의 위치에서 발사하는 것을 무제한 허용하지 않는다.
- 서버 탄환은 최초 궤적(원점·속도·서버 시각·수명·발사자·시퀀스)을 동기화한다. 클라이언트는 매 렌더 프레임에서 서버 시간 기준 직선 궤적을 계산한다. ProjectileNet의 NetworkTransform은 제거했다. 탄환마다 지속하던 위치 업데이트가 필요 없어졌다. 스폰/디스폰 메시지는 계속 사용한다.
- 같은 시퀀스의 서버 탄환이 도착하면 예측 객체를 풀에 반환하고 소유자 화면은 기존 예측 궤적·수명을 이어간다. 오래된 서버 위치로 되돌아가며 총알이 역주행하는 보정은 하지 않는다. 서버의 명중/디스폰은 그대로 적용한다. 거절된 발사도 예측 객체를 반환하며 응답이 없더라도 수명 이후 정리한다.
- 물리·데미지·처치·점수는 서버만 처리한다. 클라이언트 탄환 Rigidbody2D는 simulated=false다. 서버는 Continuous 충돌 검출과 Rigidbody 보간을 사용한다. 한 번 명중한 탄환의 중복 피해를 막고 적 피격 효과가 두 번 스폰되던 중복 경로를 제거했다.

### 몬스터·이펙트 풀

- INetworkPrefabInstanceHandler로 서버와 수신 클라이언트 모두 인스턴스를 재사용한다. Despawn(true)는 등록된 Destroy 핸들러로 반환한다. 핸들러 없이 GameObject를 파괴하던 이전 구현과 다르다.
- 풀은 스폰 메시지 직렬화 전에 탄환 상태를 준비한다. 풀 콜백도 스폰 전에 실행해 직전 속도·타이머·피격 상태가 섞이지 않게 한다. 중복 반환을 무시한다.
- 몬스터는 사망·재시작 정리 시 풀로 돌아간다. 매 스폰마다 체력·다운 상태·공격 시간·마지막 공격자·준비 상태를 초기화한다. 디스폰 시 준비 코루틴·AI·물리·콜라이더를 정리하고, 피격 색상과 파티클도 재사용 때 초기화한다.
- 풀 객체는 루트에 유지한다. NGO의 디스폰 도중 부모를 바꾸면 오류가 발생하므로 풀 정리용 parenting을 사용하지 않는다.
- EnemyNet의 끊어진 Transform 스크립트 GUID를 현재 NGO NetworkTransform으로 복구했다. 클라이언트 몬스터는 물리를 실행하지 않고 서버 위치 보간만 표시한다.

### 두 플레이어의 이동

- 이동은 기존 소유자 로컬 물리 권한을 유지한다. Rigidbody 이동을 Update로 옮기거나 서버 응답을 기다리게 하지 않았다.
- 플레이어 프리팹의 Rigidbody 보간을 켰다. NetworkRigidbody가 초기화 때 기억한 프리팹 값을 다시 적용하므로 OnNetworkSpawn에서만 보간을 켜는 것으로는 부족했다. 원격 인스턴스는 NGO Transform 보간을 사용한다.
- 대각선 이동 입력을 길이 1로 제한하고, 입력 비활성화 때 잔류 입력을 지운다. 재시작은 소유자가 Rigidbody 위치와 NetworkTransform.Teleport를 함께 갱신한다.
- 적 AI는 등록된 플레이어 목록을 사용하고 타겟 검색을 0.1초 간격으로 제한한다. 적마다 매 물리 프레임 수행하던 FindObjectsByType 검색과 결과 배열 할당을 제거했다.
- 플레이어·적의 사용하지 않는 Z 위치/X·Y 회전 동기화를 껐다. tick 30과 reliable delta 설정은 유지했다. 샘플도 reliable을 사용하므로 이를 부드러움의 원인으로 오인해 무조건 전송 방식을 바꾸지 않았다.

## 검증

Unity CLI/Pipeline으로 이 프로젝트와 Multiplayer Play Mode 가상 에디터를 지정해 실행했다. 다른 열린 프로젝트에는 명령을 보내지 않았다.

| 검증 | 결과 |
|---|---|
| Unity 컴파일 | 오류 0, 경고 0 |
| 프리팹 스크립트/권한 | Missing Script 0, 플레이어 Owner, 적 Server, 탄환은 초기 궤적 방식 |
| LAN 호스트/클라이언트 | 플레이어 2명 접속 |
| 총알 128회 + 몬스터 128회 생성·반환 | 서버 풀 80개 유지, 각 프리팹의 32개 인스턴스 재사용 |
| 수신 클라이언트 풀 | 80개 유지, 표시 탄환의 물리 비활성화 확인 |
| 실제 클라이언트 공격 | 같은 호출에서 예측 탄환 1개 생성, 서버 탄환 도착 뒤 예측 탄환 0개 |
| 서버 실제 물리 피격 | 적·탄환 디스폰, 점수 +10 |
| 사망 몬스터 재스폰 | 같은 인스턴스 재사용, 체력 5 복구 및 준비 상태 정상 |
| 지연/지터/손실 발사 | 아래 조건에서 16회 입력 즉시 표시, 정착 후 예측 잔여 0, 연결 유지, 서버 시퀀스 16 수신 |
| 최종 소유자 이동/정지 | 즉시 속도 5, 물리 시간 기준 측정 속도 5.016, 즉시 정지, 호스트·클라이언트 보간 Interpolate |
| 재접속/진행 중 탄환 | 새 클라이언트 ID로 접속, 기존 탄환의 진행된 궤적 수신, 소유자 보간 유지 |

지연 테스트는 **양쪽 피어 각각** 공식 Multiplayer Tools Network Simulator에 PacketDelayMs=100, PacketJitterMs=20, PacketLossPercent=2를 적용했다. 실제 Transport RTT 표본 16개의 중앙값은 **402ms**, 최댓값은 **427ms**였다. 설정값을 임의로 200ms RTT라고 환산하지 않았다. 이 수치는 같은 PC의 인위적 조건이며 인터넷 Relay 지연 측정이나 개선 전후 RTT 감소율이 아니다.

최종 코드 재실행에서는 RTT 중앙값 390ms, 최댓값 434ms에서도 16회 즉시 발사·예측 정리가 통과했다. 이동 테스트는 에디터의 비동기 작업 재개 시간이 정확히 1초라는 가정을 제거하고 실제 Time.fixedTime 경과로 속도를 검증했다(거리 5.217 / 물리 시간 1.040초). 테스트 종료 후 Play 모드를 종료해 인위적 지연 설정은 저장하지 않았다.

소유자 궤적 연속성을 마지막으로 다듬은 뒤에도 16회 발사 검증이 통과했다(RTT 중앙값 394ms, 최대 416ms). 클라이언트의 서버 확인 탄환 위치를 1,002회 비교했으며 진행 방향으로 역행하는 표본은 없었다. 이 표본 검사는 렌더링 영상에 대한 주관적 조작감 평가를 대체하지 않는다. 기존 AiReserializeTool의 obsolete API 경고는 별도이며 이번 수정 범위에서 변경하지 않았다.

반복 테스트에서 발견한 비스폰 객체 parenting 오류는 수정 후 동일 테스트를 다시 실행했다. 수정 후 기준 커서 이후 양쪽 콘솔에 새 오류는 없었다. 이전 개발 중 컴파일/테스트 오류는 에디터 로그에 남아 있으므로 전체 누적 콘솔 오류 수와 새 오류를 구분했다.

재실행용 스크립트는 Tools/Validation에 있다. Unity Play 모드의 LAN 호스트와 가상 클라이언트를 먼저 연결한 후 `unity command --project-path <대상 프로젝트> eval_file <스크립트 절대 경로> --result-only`로 실행한다. NetworkOptimizationSmoke/ImpactReuseSmoke는 호스트, ClientFireSmoke/ClientMovementSmoke는 클라이언트에서 실행한다. 비동기 스크립트 결과는 대상 프로젝트의 Temp/*-smoke.json에 저장된다. 테스트는 웨이브를 멈추거나 테스트 몬스터를 생성하므로 검증 후 Play 모드를 종료한다.

## 남은 제한

예측 표시가 실제 인터넷 RTT나 서버 피해 확정 시점을 줄이지는 않는다. 이번 탄환 방식은 일정 속도의 직선탄 전용이다. 유도·반사·중력·넉백 탄환을 추가할 경우 궤적 갱신 또는 다른 동기화가 필요하다. 과거 서버 물리를 되감는 lag compensation은 구현하지 않았다. 클라이언트 이동의 완전한 서버 검증·입력 재시뮬레이션도 이번 범위에 포함하지 않았다.

실제 서로 다른 두 PC의 Relay 연결, 다양한 적 수에서 Profiler CPU/GC 및 송수신 대역폭, 카메라 체감 비교는 추가 확인이 필요하다. 코드 경로상 반복 생성/검색/탄환 위치 전송은 줄였지만 실측 대역폭 절감률이나 인터넷 핑 해결 완료로 주장하지 않는다.
